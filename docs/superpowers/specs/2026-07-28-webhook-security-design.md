# Защита Topnlab webhook через query-секрет

## Статус

Утверждено 28 июля 2026 года, статус обновлён 31 июля 2026 года. Документ
описывает защиту `POST /api/webhook`. Спецификация и связанный план находятся
в ветке `fix/webhook-security`; реализация и изменение production ещё не
начинались.

Основной совместимый механизм остаётся `?secret=...`. До реализации ожидаются
ответы поддержки Topnlab о штатной подписи или заголовках, сохранении
query-параметров, формате payload, повторных попытках, timeout, кодах успеха,
частоте, тестовой отправке и IP. Эти ответы уточняют интеграцию, но не меняют
утверждённый основной вариант без отдельного решения; подтверждённый штатный
механизм может использоваться как дополнительная защита.

## Контекст

Topnlab отправляет webhook в формате
`application/x-www-form-urlencoded` с полями `id` и `type`. Текущий обработчик
принимает запрос от любого источника, затем для `type=realty` обращается к
Topnlab и обновляет PostgreSQL.

Поддержка пользовательского HTTP-заголовка со стороны Topnlab не подтверждена.
Основным совместимым механизмом становится общий секрет в полном URL:

```text
https://nedvizhimostdoneck.ru/api/webhook?secret=<случайный-секрет>
```

Секрет хранится только в защищённом `.env` production и в настройке webhook
Topnlab. В Git попадает только пустое имя переменной.

## Цели

- Отсекать неавторизованные запросы до чтения тела и вызовов CRM/БД.
- Fail closed при ошибке конфигурации.
- Ограничить тип и размер тела, а также формат идентификатора объекта.
- Перенести rate limit на Nginx, чтобы он работал для всех экземпляров Next.js.
- Не допустить секрет, query string и персональные данные в логи.
- Сохранить совместимость с текущим form-urlencoded webhook Topnlab.

## Вне scope

- HMAC-подпись или пользовательский HTTP-заголовок Topnlab.
- IP allowlist: адреса отправителя не подтверждены как стабильные.
- Изменение логики синхронизации, моделей Prisma и Topnlab API-клиента.
- Изменение `/api/lead`.
- Автоматический деплой или изменение production в рамках документации.

## Конфигурация

Добавляется обязательная серверная переменная:

```dotenv
TOPNLAB_WEBHOOK_SECRET=""
```

Production-значение должно быть независимо сгенерированной случайной строкой
не короче 32 байт. Оно не совпадает с `TOPNLAB_KEY`,
`ADMIN_SESSION_SECRET` или другими секретами.

Пустое, отсутствующее или состоящее только из пробелов значение считается
ошибкой конфигурации. Обработчик:

1. записывает только стабильное сообщение
   `topnlab_webhook_secret_not_configured`;
2. не выводит URL, query string, тело или значение переменной;
3. возвращает `503 Service Unavailable`;
4. не читает тело и не вызывает Topnlab или БД.

## Аутентификация

Ожидаемый секрет читается из `process.env.TOPNLAB_WEBHOOK_SECRET`. Полученный
секрет извлекается через `new URL(request.url).searchParams.get("secret")`.

Сравнение выполняется в отдельной чистой функции:

```ts
verifyWebhookSecret(provided: string | null, expected: string): boolean
```

Обе строки преобразуются в SHA-256 digest фиксированной длины, после чего digest
сравниваются через `timingSafeEqual`. Функция дополнительно требует непустой
полученный секрет. Такой подход исключает исключение из-за разной длины Buffer и
сохраняет постоянную длину сравниваемых данных.

Отсутствующий, пустой или неверный `?secret=` возвращает `401 Unauthorized`.
До этого ответа запрещено:

- обращаться к `request.text()`, `request.formData()` или `request.body`;
- вызывать `getEntities`;
- вызывать `upsertProperty`;
- логировать URL или переданный секрет.

## Проверка запроса

Проверки выполняются строго в следующем порядке:

1. Наличие серверной конфигурации.
2. Проверка query-секрета.
3. Проверка `Content-Type`.
4. Ограниченное чтение тела.
5. Разбор и проверка полей.
6. Вызовы Topnlab и БД.

### Content-Type

Разрешён только MIME-тип `application/x-www-form-urlencoded`. Параметр charset
разрешён и игнорируется при сравнении MIME-типа. Отсутствующий или другой тип
возвращает `415 Unsupported Media Type`.

### Размер тела

Максимальный размер тела приложения — 8 КиБ (`8_192` байта).

- Если корректный `Content-Length` больше лимита, вернуть `413` до чтения body.
- Если заголовок отсутствует или запрос передаётся chunked, читать поток с
  накоплением не более 8 КиБ и отменять reader после превышения лимита.
- Nginx повторяет внешний предел через `client_max_body_size 8k`.

### Поля

Тело разбирается через `URLSearchParams`.

- `type=realty`: `id` обязателен и должен соответствовать `^[1-9][0-9]{0,19}$`.
- `type=order`: вернуть `200 { "ok": true }` без CRM/БД, сохранив текущее
  поведение игнорирования заявок.
- Отсутствующий или неизвестный `type`: вернуть `400 Bad Request`.
- Повторяющиеся `id` или `type` считаются неоднозначным запросом и возвращают
  `400`.
- Лишние поля игнорируются для совместимости с возможным расширением payload
  Topnlab, но никогда не логируются.

## Ответы и ошибки

| Условие | HTTP | Вызов CRM/БД |
|---|---:|---|
| `TOPNLAB_WEBHOOK_SECRET` не настроен | 503 | нет |
| Секрет отсутствует или неверен | 401 | нет |
| Неверный `Content-Type` | 415 | нет |
| Тело больше 8 КиБ | 413 | нет |
| Неверные или неоднозначные поля | 400 | нет |
| `type=order` | 200 | нет |
| Корректный `type=realty` | 200 | да |
| Topnlab/БД завершились ошибкой | 502 | попытка была |

Ответы содержат только короткий стабильный код ошибки. Текст исключения,
идентификатор объекта, URL Topnlab, query string и значения окружения клиенту не
возвращаются.

Ошибка Topnlab или БД логируется стабильным сообщением
`topnlab_webhook_processing_failed` без exception message и входных данных.

## Nginx

Rate limit реализуется только на уровне Nginx:

```nginx
limit_req_zone $binary_remote_addr zone=topnlab_webhook:10m rate=60r/m;

log_format webhook_safe '$remote_addr [$time_local] "$request_method $uri" '
                        '$status $body_bytes_sent $request_time';
```

Для точного location:

```nginx
location = /api/webhook {
    client_max_body_size 8k;
    limit_req zone=topnlab_webhook burst=30 nodelay;
    limit_req_status 429;
    access_log /var/log/nginx/vizual-webhook-access.log webhook_safe;

    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

Формат `webhook_safe` использует `$uri`, а не `$request`, `$request_uri` или
`$args`; query string с секретом в access log не попадает. Перед reload
обязателен `nginx -t`.

## Тестирование

Тесты `test/webhook.test.ts` должны подтверждать:

- `503` и отсутствие чтения body/CRM/БД без переменной окружения;
- `401` и отсутствие чтения body/CRM/БД без query-секрета;
- `401` при неверном секрете;
- успешное сравнение секрета через публичный интерфейс обработчика;
- `415` для неверного Content-Type;
- `413` по `Content-Length`;
- `413` для chunked/streamed тела;
- `400` для отсутствующего, нулевого, отрицательного, слишком длинного,
  нечислового или повторяющегося `id`;
- `400` для отсутствующего, неизвестного или повторяющегося `type`;
- `type=order` не вызывает CRM/БД;
- корректный `type=realty` вызывает `getEntities` и `upsertProperty` ровно один
  раз;
- ошибки CRM/БД дают безопасный `502` без секрета, query string, ID и exception
  message;
- ни один отказ не печатает секрет или payload в `console`.

После точечных тестов обязательны полный `npm test`, `npx tsc --noEmit`,
`npm run lint` и `npm run build`.

## Развёртывание

1. Сгенерировать отдельный случайный секрет без вывода в историю shell.
2. Записать его в защищённый production `.env` с режимом `0600`.
3. Зарегистрировать в Topnlab полный HTTPS URL с `?secret=...`.
4. Добавить Nginx zone, безопасный log format и точный location.
5. Выполнить `nginx -t`, затем reload Nginx.
6. Перезапустить приложение после обновления `.env`.
7. Проверить `401`, `415`, `413`, `429` и штатный webhook.
8. Убедиться, что access/error/application logs не содержат query string,
   секрета, ID или payload.

Production изменяется только после отдельного подтверждения пользователя и
наличия резервной точки отката.
