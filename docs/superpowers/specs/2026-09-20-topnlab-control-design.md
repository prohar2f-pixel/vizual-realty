# Тестовый контур контроля Topnlab

## Цель

Создать отдельное защищённое приложение `control.nedvizhimostdoneck.ru` для проверки расхождений между источниками Topnlab и опубликованным каталогом сайта «Визуал».

Контур предназначен для тестирования и доработки перед передачей заказчику. Он не меняет Topnlab, боевой сайт, его базу данных или штатную синхронизацию.

## Подтверждённый исходный факт

Контрольная проверка 18 сентября 2026 года показала, что разные источники Topnlab возвращают неодинаковые наборы объектов:

- интерфейс Topnlab показывал 403 объекта;
- публичный API активных объектов с `is_feed=true` вернул 354 ID;
- XML-фид, который использует сайт, содержал 335 ID;
- в базе сайта было опубликовано 335 ID, полностью совпадающих с XML-фидом.

Следовательно, тестовый продукт должен показывать не только разницу Topnlab ↔ сайт, но и конфликт между XML-фидом и API Topnlab.

## Границы и запреты

Приложение:

- читает XML-фид Topnlab;
- читает API Topnlab;
- читает данные опубликованного каталога из базы сайта;
- хранит собственные результаты проверок в отдельной базе данных контура;
- не выполняет POST/PUT/PATCH/DELETE-запросы в Topnlab;
- не пишет в боевую базу сайта;
- не запускает и не изменяет штатную синхронизацию сайта;
- не отправляет уведомления в Telegram на первом этапе.

## Архитектура

```text
XML-фид Topnlab ─┐
                 ├─> control: сбор снимка ─> правила ─> собственная БД ─> веб-панель
API Topnlab ─────┤
                 │
База сайта ──────┘
```

`control` разворачивается как отдельное Next.js-приложение и отдельный PM2-процесс на существующем VPS. Для него используются собственные переменные окружения и отдельная учётная запись входа. Боевой сайт продолжает работать независимо.

## Источники и проверяемые наборы

Для одного запуска создаются три множества ID:

1. `xmlFeedIds` — ID офферов из XML-фида Topnlab.
2. `apiActiveIds` — ID, возвращённые API Topnlab как активные объекты с `is_feed=true`.
3. `sitePublishedIds` — ID объектов с признаком публикации в базе сайта.

Панель показывает размер каждого множества и четыре точные группы расхождений:

- есть в XML-фиде, отсутствует на сайте;
- опубликовано на сайте, отсутствует в XML-фиде;
- есть в API, отсутствует в XML-фиде;
- есть в XML-фиде, отсутствует в API.

Эти проверки строятся только на сравнении ID и не требуют предположений о корректности полей.

## Проверки качества полей

Для объектов XML-фида, для которых API вернул карточку, контур собирает диагностические записи следующих типов:

- отсутствуют фотографии;
- цена отсутствует или не является положительным числом;
- для квартиры отсутствуют комнаты, этаж или этажность;
- отсутствует город;
- отсутствует менеджер;
- API не вернул карточку объекта, присутствующего в XML-фиде.

Нестандартные города, районы и типы объектов на первом этапе относятся к категории «Требует проверки», а не к автоматическим ошибкам. Правило может стать строгим только после ручной валидации на реальных карточках.

## Модель данных контура

Контур хранит независимые от боевого сайта записи:

- `AuditRun`: время запуска, длительность, состояние, размеры трёх множеств, техническая ошибка запуска при наличии;
- `AuditIssue`: код правила, ID объекта, категория, текст причины, источник, ответственный менеджер при наличии, время первого и последнего обнаружения, статус;
- `AuditIssueObservation`: привязка проблемы к конкретному запуску для истории.

Статусы проблемы: `open`, `resolved`, `review`.

Если проблема не повторилась в следующем успешном запуске, контур помечает её как `resolved`; он не удаляет историю.

## Интерфейс

Главный экран содержит:

- показатели XML-фида, API Topnlab и опубликованного каталога;
- дату, длительность и итог последнего запуска;
- кнопку «Проверить сейчас»;
- вкладки «Точные ошибки», «Неполные данные», «Требует проверки», «Исправленные»;
- фильтры по ID объекта, категории и ответственному;
- строку проблемы с причиной, источником, ответственным, датой обнаружения и ссылкой «Открыть в Topnlab».

Ссылка только открывает карточку Topnlab в браузере. Исправление данных выполняется сотрудником в Topnlab.

## Запуски и обработка ошибок

Контур поддерживает ручной запуск из интерфейса и плановый запуск раз в час после штатной синхронизации сайта. Одновременно допускается только один запуск.

Если источник не отвечает, XML не содержит офферов или API возвращает неполные данные, запуск получает статус ошибки. Ранее открытые проблемы не закрываются после неуспешного запуска.

## Доступ и безопасность

- Отдельные логин, хэш пароля и секрет сессии хранятся только в переменных окружения сервера.
- Сессия реализуется зашифрованной cookie с ограниченным сроком действия.
- Все запросы интерфейса требуют действующую сессию и проверку Origin.
- Секреты Topnlab, доступ к базе и журналы с персональными данными не выводятся в интерфейс и не попадают в Git.
- Доступ к боевой базе организуется учётной записью PostgreSQL только на чтение.

## Критерии тестовой приёмки

1. Контур воспроизводит контрольную сверку: показывает равенство XML-фида и опубликованных ID сайта, если множества совпадают.
2. Контур показывает отдельные списки расхождений XML ↔ API Topnlab.
3. На тестовом объекте с отсутствующим обязательным полем создаётся проблема нужной категории.
4. После исправления объекта в Topnlab и успешного следующего запуска проблема помечается `resolved`.
5. Никакой запуск не изменяет Topnlab, боевой сайт или боевую базу данных.
6. При ошибке источника панель показывает ошибку запуска и не закрывает существующие проблемы.

## Отложенный этап

После проверки точности правил возможно включение Telegram-уведомлений только о новых проблемах, ошибках запуска и существенном изменении количества объектов. Для этого потребуется отдельный бот, чат назначения и хранение токена в защищённых переменных сервера.
