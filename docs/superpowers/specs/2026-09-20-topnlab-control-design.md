# Тестовый контур контроля Topnlab

## Цель и границы

Создать отдельное защищённое приложение `control.nedvizhimostdoneck.ru` для проверки состава и качества данных, передаваемых между Topnlab и опубликованным каталогом сайта «Визуал».

Контур нужен для тестирования и доработки перед передачей заказчику. Он **не изменяет** Topnlab, боевой сайт, его базу данных или штатную синхронизацию: только читает источники и записывает результаты в собственную БД.

Первый релиз не отправляет сообщения в Telegram и не исправляет карточки автоматически. Сотрудник исправляет данные только в Topnlab.

## Подтверждённое исходное состояние

Контрольная проверка 18 сентября 2026 года дала следующие результаты:

- интерфейс Topnlab показывал 403 объекта;
- API активных объектов с `is_feed=true` вернул 354 ID;
- XML-фид, который использует сайт, содержал 335 ID;
- в базе сайта было 335 опубликованных ID, совпадающих с ID XML-фида.

В той проверке различались API и XML: 52 ID были только в API, 33 — только в XML, всего 85 направленных расхождений. Это не доказывает, что одна из систем ошибочна: контур должен зафиксировать и показать разницу с её источником и временем снимка.

## Архитектура

```text
XML-фид Topnlab ─┐
API Topnlab ─────┼─> адаптеры источников ─> канонизация ID ─> движок правил
База сайта ──────┘                                         │
                                                          ├─> отдельная БД control
                   control-worker (плановый/ручной запуск)│
                                                          └─> control-web (панель)
```

`control-worker` и `control-web` — два отдельных PM2-процесса на существующем VPS. У них свой каталог, собственные переменные окружения и отдельная БД. Боевой сайт продолжает работать независимо.

Слой адаптеров не содержит правил качества; слой канонизации не делает сетевых запросов; движок правил не обращается к Topnlab напрямую. Такое разделение позволяет тестировать каждую часть независимо.

## Контракты источников и снимки

Каждый запуск создаёт отдельные снимки источников. Снимки не считаются атомарными между разными системами: в отчёте всегда сохраняются время начала и окончания чтения каждого источника, число записей, контрольная сумма отсортированных ID, состояние и текст технической ошибки без секретов.

| Источник | Способ чтения | Проверяемый результат | Ограничения и реакция на сбой |
| --- | --- | --- | --- |
| XML-фид | HTTP GET по настроенному `TOPNLAB_FEED_URL` | XML, офферы `<offer internal-id="…">`, число валидных ID | пустой/некорректный XML — снимок `failed`; сравнения, требующие XML, пропускаются |
| API Topnlab | существующие методы получения ID и карточек | список ID, карточки объектов, HTTP-статус | ограничение пакета, паузы и повторы определяются отдельным контрактным тестом перед подключением; после исчерпания утверждённых попыток снимок `failed` или `partial` |
| База сайта | PostgreSQL-учётная запись только на чтение | `Property.id` с `isFeed=true` | запрос выполняется в read-only транзакции; ошибка не позволяет закрывать проблемы, зависящие от сайта |

Текущая реализация сайта сопоставляет XML `internal-id` и `Property.id` напрямую. В control это принимается только после контрактного теста, который на фиксированных примерах подтверждает такое соответствие. Если источник изменит формат или появятся разные типы ID, адаптер обязан сохранить исходный ID и явное сопоставление в `ObjectMapping`; сравнение «по строке как есть» не считается универсальным правилом.

Перед включением нового поля или нового источника добавляется контрактный тест его фактического формата. Предположения о пагинации, кодах статуса или полях, не подтверждённых текущим клиентом Topnlab, в продукт не закладываются.

## Составные проверки

После успешного чтения доступных снимков создаются четыре направленные группы:

- есть в XML-фиде, отсутствует среди опубликованных на сайте;
- опубликовано на сайте, отсутствует в XML-фиде;
- есть в API, отсутствует в XML-фиде;
- есть в XML-фиде, отсутствует в API.

Для каждого результата сохраняются ID в каноническом и исходном виде, источники, значения/состояния источников, ссылка на карточку Topnlab (если шаблон ссылки подтверждён) и доказательство сравнения. Это позволяет отличить расхождение источников от ошибки синхронизации сайта.

## Проверки качества данных

Качество полей проверяется только для объекта, который удалось однозначно сопоставить с карточкой API. Для каждого правила хранится версия, область действия, перечень полей-источников и уровень достоверности результата.

Стартовый каталог правил:

| Правило | Область | Результат при отсутствии/некорректности |
| --- | --- | --- |
| `api-card-missing` | ID есть в XML, но API не вернул карточку после успешного чтения API | точная ошибка |
| `photo-missing` | только объект, для которого продуктовая политика явно требует фото | неполные данные |
| `price-invalid` | только объект с числовым полем цены по контракту источника | неполные данные |
| `flat-details-missing` | только квартира: комнаты, этаж, этажность | неполные данные |
| `city-missing` | объект, в котором город передаётся источником | неполные данные |
| `manager-missing` | объект, в котором менеджер передаётся источником | неполные данные |

Нестандартные города, районы, типы, нулевые цены, студии и объекты без фотографий не объявляются автоматической ошибкой, пока заказчик не утвердит для них политику. Они могут отображаться как «Требует проверки» с исходным значением и объяснением правила. Это исключает ложные срабатывания для объектов, где поле не применимо.

Матрица приоритета: API Topnlab — первичный источник полей; XML — источник включения в фид; база сайта — зеркало опубликованного состояния. Значение на сайте не используется для автоматического признания значения Topnlab неверным.

## Модель данных и жизненный цикл

Контур хранит только собственные записи:

- `AuditRun`: идентификатор, плановый/ручной запуск, время, длительность, состояние `success`/`partial`/`failed`, версия набора правил;
- `SourceSnapshot`: запуск, источник, окно чтения, количество, хэш, состояние, техническая ошибка;
- `ObjectMapping`: исходный ID источника, канонический ID, способ и версия сопоставления;
- `AuditIssue`: ключ `(код правила, канонический ID)`, категория, доказательство, источник, ответственный при наличии, время первого/последнего обнаружения, пользовательский статус;
- `AuditIssueObservation`: наблюдение проблемы в конкретном запуске, состояние `seen`/`not_seen`/`skipped`, применённая версия правила;
- `AuditAction`: только действия в control — ручной запуск, перевод в `review`/`ignored`, комментарий, автор и время.

Статусы проблемы: `open`, `review`, `ignored`, `resolved`, `stale`.

Проблема становится `resolved` лишь когда успешный запуск получил **полное покрытие** всех источников и полей, требуемых данным правилом, объект всё ещё находится в области правила, и проблема не повторилась. При `partial`/`failed`, пропущенном источнике или неоценённом правиле она не закрывается, а помечается `stale` либо сохраняет текущий статус. История не удаляется.

## Запуски, конкуренция и отказоустойчивость

Плановый запуск выполняется раз в час после штатной синхронизации сайта. Ручной запуск создаётся кнопкой «Проверить сейчас» и фиксируется в `AuditAction`.

Единственность запуска обеспечивается PostgreSQL advisory lock, удерживаемым worker на всё время проверки. При занятой блокировке ручной запрос получает понятный ответ «проверка уже идёт», плановый запуск пропускается с записью в журнале. In-memory флаг не используется как единственная защита.

Если недоступен один источник, worker сохраняет `partial` или `failed` и выполняет только те сравнения, для которых достаточно успешно полученных снимков. Он не создаёт массовые новые проблемы из-за недоступного источника и не закрывает старые.

`/health` проверяет, что процесс отвечает; `/ready` дополнительно проверяет доступность собственной БД. Панель показывает дату последнего успешного и последнего неуспешного запуска, состояние каждого источника и причину ошибки.

## Интерфейс

Главный экран содержит:

- показатели XML-фида, API Topnlab и опубликованного каталога с временем каждого снимка;
- состояние, длительность, версию правил и покрытие последнего запуска;
- кнопку «Проверить сейчас» и защиту от повторного запуска;
- вкладки «Точные расхождения», «Неполные данные», «Требует проверки», «Исправленные», «История запусков»;
- фильтры по ID, коду правила, источнику, категории, ответственному и статусу;
- строку проблемы с исходным/каноническим ID, доказательством, ответственным, временем, состоянием покрытия и ссылками «Открыть в Topnlab»/«Открыть на сайте» при наличии;
- перевод проблемы в `review` или `ignored` с комментарием; эти действия не меняют Topnlab.

## Доступ и безопасность

- Логин, хэш пароля, секрет сессии, доступы Topnlab и БД хранятся только в переменных окружения сервера.
- Cookie: `HttpOnly`, `Secure`, `SameSite=Strict`, ограниченный срок жизни; сессия проверяется на каждом запросе.
- Все изменяющие действия требуют действующую сессию, CSRF-токен и проверку Origin; вход ограничивается по частоте попыток.
- Включаются HSTS, CSP с `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff` и запрет встраивания во фрейм.
- Учётная запись к боевой PostgreSQL имеет только `CONNECT` и `SELECT` на требуемые таблицы/представление; прав записи, DDL и доступа к другим данным у неё нет.
- В тестовом контуре рекомендуется включить IP allowlist. До передачи заказчику доступ усиливается вторым фактором (TOTP) либо утверждённым заказчиком VPN/IP allowlist.
- Секреты и персональные данные не выводятся в интерфейс и не попадают в Git, логи или тексты ошибок.

## Проверки и критерии приёмки

1. Контрактные тесты XML, API и БД проверяют фактический формат ID, пустые ответы и ошибочные ответы; изменение формата не приводит к молчаливому сравнению неправильных ID.
2. На фикстурах 335 одинаковых ID контур показывает ноль расхождений XML ↔ сайт.
3. На фикстуре с одним дополнительным ID XML контур показывает ровно одно расхождение «есть в XML, нет на сайте».
4. На фикстуре, воспроизводящей измеренное состояние 354 API-ID и 335 XML-ID, контур показывает 52 API-only и 33 XML-only записи, всего 85 направленных расхождений.
5. На карточке с отсутствующим полем создаётся только применимое правило и сохраняется версия правила, значение поля и источник доказательства.
6. После успешного полного запуска, в котором применимое правило перестало срабатывать, проблема получает `resolved`; при `partial`/`failed` она не закрывается.
7. Параллельный ручной и плановый запуск не могут выполняться одновременно.
8. Автотесты доказывают отсутствие write-вызовов к Topnlab и отсутствие записи в боевую БД; интеграционный тест использует read-only учётную запись.
9. Негативные тесты покрывают недоступность XML, API 429/5xx, частичную загрузку карточек, пустой XML и недоступность БД.
10. Тесты доступа проверяют отсутствие доступа без сессии, CSRF/Origin-проверку и rate limit входа.

## Отложенный этап

После подтверждения точности правил можно подключить уведомления только о новых точных расхождениях, сбоях запусков и существенном изменении количества объектов. Канал (Telegram, email или webhook), получатели и срок хранения данных утверждаются отдельно; токены остаются в защищённых переменных сервера.
