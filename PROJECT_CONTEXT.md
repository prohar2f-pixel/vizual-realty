## Стек и структура

- Next.js 16.2.12, React 19, TypeScript, Tailwind CSS.
- Prisma 7 и PostgreSQL.
- Topnlab API, собственные скрипты синхронизации.
- Nginx + PM2 на Ubuntu 22.04 в Beget VPS.

Ключевые файлы:

- `src/lib/site-content/published.ts` и `src/lib/site-content/store.ts` — текущий request-scoped источник публичных карточек команды и остальных текстов: проверенное значение `SiteContent.published` из PostgreSQL.
- `src/lib/site-content/defaults.ts` — встроенный legacy fallback с карточками команды; используется только при ожидаемой недоступности БД, отсутствии или невалидности сохранённого `SiteContent`, а не как основной источник после публикации.
- `src/app/(public)/team/page.tsx` и `src/app/(public)/contacts/page.tsx` — публичные потребители опубликованной команды; контакты также выводят данные офиса и карту.
- `src/lib/manager-profiles.ts` — разрешённые профили менеджеров для объектов, ключ — ID сотрудника Topnlab.
- `src/lib/topnlab/manager.ts` — определение менеджера объекта по ID, затем резервно по имени.
- `src/lib/topnlab/map.ts` — преобразование объекта Topnlab в модель сайта.
- `src/lib/topnlab/content.ts` — нормализация адресов, районов и описаний.
- `src/app/api/lead/route.ts` — отправка формы заявки в Topnlab.
- `scripts/sync.ts`, `scripts/sync-property-content.ts`, `scripts/sync-managers.ts` — ручная синхронизация.
- `prisma/schema.prisma` — модели `Property` и `Agent`.
- `src/lib/admin/` — зашифрованная cookie-сессия, вход и защита изменяющих запросов.
- `src/lib/site-content/` — строгая схема, встроенный резерв и версии контента.
- `src/lib/featured.ts` — чтение и транзакционное сохранение избранных объектов.
- `src/lib/team-images.ts` — проверка, преобразование, выдача и очистка фотографий команды.
- `scripts/seed-admin-content.ts` — идемпотентное первоначальное заполнение админ-данных.
- `scripts/cleanup-team-images.ts` — удаление неиспользуемых фотографий старше 24 часов.
- `docs/superpowers/specs/` и `docs/superpowers/plans/` — подробные решения по отдельным доработкам.

Важно: для этой версии Next.js перед изменением фреймворк-зависимого кода читать соответствующую документацию в `node_modules/next/dist/docs/`, как требует `AGENTS.md`.

## Локальный запуск и проверка

На Windows использовать `npm.cmd`, потому что PowerShell может блокировать `npm.ps1`.

```powershell
npm.cmd install
npm.cmd run dev -- -p 3100
```

Для проверки режима, максимально близкого к продакшену:

```powershell
npm.cmd test
npx.cmd tsc --noEmit
npm.cmd run lint
npm.cmd run build
npm.cmd run start -- -p 3100
```

Перед заявлением о готовности обязательно запустить тесты и build. В проекте есть старые lint-ошибки `no-explicit-any` в `src/lib/topnlab/client.ts`, `src/lib/topnlab/manager.ts`, `src/lib/topnlab/map.ts` и предупреждения в `test/map-realty-type.test.ts`; новые или изменённые файлы должны проходить lint без новых ошибок.

Миграционная репетиция 26 июля 2026 года выполнена на отдельном временном loopback PostgreSQL 17 без `.env` и production URL. Проверены оба пути: чистая установка двух миграций и upgrade существующей схемы `Agent`/`Property` через строгий preflight и `prisma migrate resolve --applied 20260710000000_initial_catalog_baseline`. В обоих случаях seed дважды дал одну строку `SiteContent`, восемь сотрудников и три избранных объекта; существующие объекты upgrade сохранились. Реальный wrapper успешно выполнил backup и preflight из одного Prisma URL с `schema=public`. Отдельные повреждённые схемы с неправильными PK/FK, `integer[]` вместо `text[]`, лишним обязательным столбцом, частичной migration history и существующей admin-таблицей были отклонены. Временный cluster остановлен, его точный каталог удалён.

## Админ-панель и серверные данные

Обязательные переменные без значений: `ADMIN_USERNAME`, `ADMIN_PASSWORD_HASH`, `ADMIN_SESSION_SECRET`, `SITE_ORIGIN`, `TEAM_UPLOAD_DIR`, `DATABASE_URL`. `ADMIN_SESSION_TTL_HOURS` необязателен и по умолчанию равен 12 часам. `SITE_URL`, `TOPNLAB_KEY` и `TOPNLAB_BASE_URL` сохраняют прежнее назначение.

- В `.env` хранится только scrypt-хеш пароля, открытый пароль не хранится.
- `ADMIN_SESSION_SECRET` должен содержать не менее 32 случайных байт.
- `SITE_ORIGIN` — `https://nedvizhimostdoneck.ru` без завершающего слеша.
- Рекомендуемый production `TEAM_UPLOAD_DIR`: `/home/vizual/data/team-uploads`, режим `0750`, владелец и группа процесса PM2.
- Nginx должен ограничивать тело запроса входа небольшим размером и отдельно разрешать до 11 МиБ для загрузки фото команды.
- Ежедневно запускать `scripts/cleanup-team-images.ts` с серверным `.env`; используемые в draft, published или previousPublished изображения не удаляются.

Безопасная генерация scrypt-хеша и session secret без вывода значений описана в `README.md`.

## Синхронизация Topnlab

Переменные `DATABASE_URL`, `TOPNLAB_KEY`, `TOPNLAB_BASE_URL` находятся в `.env`. Это действующие секреты: не печатать их в терминал, не вставлять в чат и не коммитить.

```powershell
npm.cmd run sync
npm.cmd run sync:content
npm.cmd run sync:managers
```

- `sync` получает все объекты продажи и аренды, находящиеся в фиде, и обновляет базу.
- `sync:content` повторно нормализует адреса, районы и описания существующих объектов.
- `sync:managers` повторно связывает объекты с известными менеджерами.

Объект попадёт на сайт только после включения его в фид в Topnlab. После изменений в Topnlab выполнить синхронизацию на сервере и проверить несколько объектов от разных сотрудников.

## Git и публикация

Перед коммитом:

1. Проверить `git status --short --branch` и не трогать посторонние изменения пользователя.
2. Выполнить тесты и build.
3. Получить `origin/main` и убедиться, что отправка будет fast-forward.
4. Коммитить только файлы текущей задачи.

Продакшен-проект на сервере: `/home/vizual/app`, процесс PM2: `vizual`. Для фотографий использовать `/home/vizual/data/team-uploads`, для резервных копий — `/home/vizual/backups/<UTC-время>`.

Порядок выпуска админ-панели: в одном fail-fast shell с выключенной трассировкой один раз загрузить неизменный `DATABASE_URL` из защищённого `.env` → передать его Prisma напрямую, а `pg_dump`/`psql` через `scripts/run-postgres-tool.mjs`, который производит libpq env без передачи URL дочернему процессу → проверить чистый Git → записать предыдущий commit → получить `origin/main` с wrapper → backup PostgreSQL/uploads → создать постоянную папку uploads → `npm ci` → для существующей БД выполнить строгий preflight и один раз отметить baseline применённым → `npx prisma migrate deploy` → дважды проверить идемпотентный seed → `npm run build` → удалить переменные БД из shell → `pm2 restart vizual` → smoke test публичных страниц и `/admin`. Точные команды без URL/пароля/хеша в аргументах или выводе находятся в `README.md`.

Откат приложения выполняется переключением на записанный предыдущий commit, `npm ci`, повторной сборкой и рестартом PM2. Новая схема добавочная и совместима со старым кодом: миграцию назад не выполнять, published-данные и uploads не удалять. Восстановление backup БД/uploads допустимо только при подтверждённом повреждении данных, потому что оно уничтожит более новые изменения.

В VNC-терминале Beget символы `&&` вводились как `77`, поэтому использовать `set -e;` и команды через `;`. Для сервера открывать терминал VPS **Genial Sable**, а не SSH виртуального хостинга. SSH виртуального хостинга оставлять выключенным.

После деплоя обязательно проверить живой сайт, особенно `/team`, `/contacts`, `/catalog`, открытую карточку объекта, вход `/admin`, избранные, предпросмотр, публикацию и доступность отката.

## Утверждённые принципы

- Сначала показывать локальный результат пользователю, затем публиковать, если пользователь не попросил сразу обновить живой сайт.
- Качество фотографий не снижать заметной агрессивной компрессией.
- Аватары менеджеров — в зелёной рамке.
- Не очищать и не сбрасывать dirty worktree без прямого разрешения.
- Любое действие можно откатить Git-коммитом; перед рискованными изменениями записывать текущий hash `main`.
